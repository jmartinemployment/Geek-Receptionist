# The OAuth redirect error contract Entra ID returns to a multi-tenant app's redirect_uri when consent is blocked, required, or refused

Research date: 2026-11-21. All quotes are verbatim from the en-us Microsoft Learn pages as fetched (full raw HTML downloaded with curl, not truncated summaries). Each page's own `ms.date` metadata is noted. Context: confidential web app, server-side authorization code flow, delegated `Calendars.ReadWrite` + `offline_access`, work/school user in a foreign tenant. Per Microsoft's own rule (quoted in full under question 3), the plan must classify only on the OAuth `error` query parameter; AADSTS numbers are log-level corroboration only.

## Key question 1 — Scenario matrix: which `error` value arrives at the redirect_uri in each consent-failure scenario

### Takeaway
Microsoft documents the redirect `error` vocabulary for the /authorize endpoint as a closed table: `invalid_request`, `unauthorized_client`, `access_denied`, `unsupported_response_type`, `server_error`, `temporarily_unavailable`, `invalid_resource`, `login_required`, `interaction_required`. Of the six scenarios, only two are classifiable from primary documentation: a plain user Cancel/Deny on the consent prompt is `access_denied` (Microsoft's own example redirect), and `prompt=none` before consent exists is `interaction_required` (or `login_required` when no single signed-in user is found). For the consent-blocked / admin-approval-interrupt scenarios (1, 2, 3, 5), Microsoft documents the interrupt screens and the AADSTS codes shown **on** them, but publishes no statement of what reaches the redirect_uri when the user exits those screens — that is NOT CONFIRMED from primary docs (community evidence points to `access_denied`, noted under Inferences).

### Cited Findings

**The documented authorization-endpoint error table (the full vocabulary the plan can branch on).** "The following table describes the various error codes that can be returned in the `error` parameter of the error response." The rows, verbatim (Error Code | Description | Client Action):
- `invalid_request` | "Protocol error, such as a missing required parameter." | "Fix and resubmit the request. This error is a development error typically caught during initial testing."
- `unauthorized_client` | "The client application isn't permitted to request an authorization code." | "This error usually occurs when the client application isn't registered in Microsoft Entra ID or isn't added to the user's Microsoft Entra tenant. ..."
- `access_denied` | "Resource owner denied consent" | "The client application can notify the user that it can't continue unless the user consents."
- `unsupported_response_type` | "The authorization server doesn't support the response type in the request." | "Fix and resubmit the request. ..."
- `server_error` | "The server encountered an unexpected error." | "Retry the request. These errors can result from temporary conditions. ..."
- `temporarily_unavailable` | "The server is temporarily too busy to handle the request." | "Retry the request. ..."
- `invalid_resource` | "The target resource is invalid because it doesn't exist, Microsoft Entra ID can't find it, or it's not correctly configured." | "This error indicates the resource, if it exists, hasn't been configured in the tenant. ..."
- `login_required` | "Too many or no users found." | "The client requested silent authentication (prompt=none), but a single user couldn't be found. This error may mean there are multiple users active in the session, or no users. This error takes into account the tenant chosen. For example, if there are two Microsoft Entra accounts active and one Microsoft account, and consumers is chosen, silent authentication works."
- `interaction_required` | "The request requires user interaction." | "Another authentication step or consent is required. Retry the request without prompt=none."
— [Microsoft identity platform and OAuth 2.0 authorization code flow, § Error codes for authorization endpoint errors](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) (ms.date 2026-01-09)

**Scenario 4 — user plainly clicks Cancel/Deny on an ordinary consent prompt → `access_denied`.** Microsoft's own example of the redirect error response is literally the cancel case: "Error responses may also be sent to the redirect_uri so the app can handle them appropriately:" followed by `GET http://localhost?` `error=access_denied` `&error_description=the+user+canceled+the+authentication` — [v2-oauth2-auth-code-flow, § Error response](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow). The same example appears on the OIDC page: "Error responses might also be sent to the redirect URI so the app can handle them, for example: ... `error=access_denied&error_description=the+user+canceled+the+authentication`" — [Microsoft identity platform and OpenID Connect protocol, § Error response](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc) (ms.date 2026-06-30). The matching AADSTS log-side code: "AADSTS65004 | UserDeclinedConsent - User declined to consent to access the app. Have the user retry the sign-in and consent to the app" — [reference-error-codes](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes).

**Scenario 6 — `prompt=none` before any consent exists → `interaction_required` (or `login_required` if no single session).** The `prompt` parameter doc: "prompt=none is the opposite. It ensures that the user isn't presented with any interactive prompt. If the request can't be completed silently by using single-sign on, the Microsoft identity platform returns an interaction_required error." — [v2-oauth2-auth-code-flow, request-parameters table](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow). The table rows for `login_required` and `interaction_required` are quoted in full above; `interaction_required`'s client action — "Another authentication step or consent is required. Retry the request without prompt=none." — explicitly covers the missing-consent case. The OIDC page adds the causes: "If the request can't be completed silently via single sign-on, the Microsoft identity platform returns an error. Causes include no signed-in user, the hinted user isn't signed in, or multiple users are signed in but no hint was provided." — [v2-protocols-oidc, prompt parameter](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc).

**Where `consent_required` is documented.** It is NOT in the authorization-endpoint error table. It appears in two places:
1. In the auth-code-flow **token endpoint** error table: "`consent_required` | The request requires user consent. This error is non-standard. It's usually only returned on the /authorize endpoint per OIDC specifications. Returned when a scope parameter was used on the code redemption flow that the client app doesn't have permission to request. | The client should send the user back to the /authorize endpoint with the correct scope to trigger consent." — [v2-oauth2-auth-code-flow, § Error codes for token endpoint errors](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
2. As the documented redirect error of the dedicated **admin consent endpoint** (`/adminconsent`, i.e. when a tenant admin is walked through the admin-consent URL and declines): the documented error response is `http://localhost/myapp/permissions ?admin_consent=True &error=consent_required &error_description=AADSTS65004%3a+The+resource+owner+or+authorization+server+denied+the+request.%0d%0aTrace+ID%3a+... &state=12345` — [Admin consent on the Microsoft identity platform, § Error response](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent) (ms.date 2023-11-08). Note the documented example carries `admin_consent=True` even in the error case — quoted exactly as the page shows it.

**Scenario 1 — tenant consent policy blocks user consent, admin consent workflow DISABLED.** What Microsoft documents is the on-screen interrupt, not a redirect: among the symptom messages "you receive an error message similar to one of the following examples: Need admin approval ... AADSTS90094: An administrator of <TenantDisplayName> has set a policy that prevents you from granting <Name-of-App> the permissions it is requesting. Contact an administrator of <TenantDisplayName>, who can grant permissions to this app on your behalf." and among the listed causes: "User consent is disabled at the tenant level." — [Troubleshoot consent issues in Microsoft Entra ID](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshoot-consent-issues) (ms.date 2025-01-15). No Microsoft page found states which OAuth `error` value reaches the redirect_uri when the user leaves this screen → NOT CONFIRMED (see Inferences).

**Scenarios 2 and 3 — workflow ENABLED: user submits a request, or cancels the "Need admin approval" screen.** Microsoft documents the experience only up to the screen and the email loop: "When you configure the admin consent workflow, your users can request consent directly through the prompt." and "When an administrator responds to a request, the user receives an email alert that says the request is processed." — [Overview of admin consent workflow](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/admin-consent-workflow-overview) (ms.date 2024-11-29). The configuration page likewise describes reviewers, expiry and notifications with no redirect contract — [Configure the admin consent workflow](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-admin-consent-workflow) (ms.date, page fetched 2026-11-21). Neither page states what the app's redirect_uri receives on submit or on cancel → NOT CONFIRMED from primary docs.

**Scenario 5 — risk-based step-up consent blocks an unverified publisher's app.** "When a risky consent request is detected, the consent prompt displays a message that indicates that admin approval is needed. If the admin consent request workflow is enabled, the user can send the request to an admin for further review directly from the consent prompt. If the admin consent request workflow isn't enabled, the following message is displayed: AADSTS90094: <clientAppDisplayName> needs permission to access resources in your organization that only an admin can grant. Request an admin to grant permission to this app before you can use it." — [Configure risk-based step-up consent using PowerShell](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-risk-based-step-up-consent) (ms.date 2025-05-21). What triggers it: "Beginning November 2020, if risk-based step-up consent is enabled, users can't consent to most newly registered multitenant apps that aren't publisher verified. The policy applies to apps that were registered after November 8, 2020, which use OAuth 2.0 to request permissions that extend beyond the basic sign-in and read user profile, and which request consent from users in tenants that aren't the tenant where the app is registered." — [Publisher verification overview](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview) (ms.date 2024-08-13). The step-up log-side codes: "AADSTS900941: Administrator consent is required. App is considered risky. (AdminConsentRequiredDueToRiskyApp) This app may be risky. If you trust this app, ask your admin to grant you access." and "AADSTS900981: An admin consent request was received for a risky app. (AdminConsentRequestRiskyAppWarning) This app may be risky. Only continue if you trust this app." — [Troubleshoot consent issues](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshoot-consent-issues). Again, this blocks at the consent prompt (it becomes the same "needs admin approval" interrupt); the redirect `error` value is not documented → NOT CONFIRMED.

### Inferences
- The six scenarios collapse into three classifiable buckets on the `error` parameter: (a) `access_denied` = any interactive path the user did not complete with a grant — plain deny, and (per community evidence below, unconfirmed by Microsoft) exiting the "Need admin approval" interrupt whether or not a request was submitted; (b) `interaction_required` / `login_required` = silent (`prompt=none`) requests that need interaction — treat both as "send the user through interactive auth"; (c) `consent_required` = documented on the `/adminconsent` endpoint decline and defined by OIDC for `prompt=none`; a robust classifier should accept it in the consent-needed bucket even though the /authorize table omits it, since Microsoft itself calls it "usually only returned on the /authorize endpoint per OIDC specifications."
- Community evidence (guides, does NOT ground a claim): a Microsoft Q&A thread surfaced in search shows the admin-approval interrupt returning `https://my-app.com/oauth/authorized?error=access_denied&error_subcode=cancel&state={state}&error_description=AADSTS65004%3a+User+declined+to+consent+to+access+the+app.` — i.e. scenarios 1–3 arriving as `access_denied` with an undocumented `error_subcode=cancel` and AADSTS65004 in the description (community post on learn.microsoft.com/en-us/answers/, surfaced via search snippet; the exact thread was not re-fetched and this is user-posted content, not documentation). Consistent with classifying the whole blocked/refused family as `access_denied`, but the plan must not depend on `error_subcode` existing — it appears in no Microsoft reference (see question 2).
- Because scenarios 1, 2, 3, 4 and 5 are indistinguishable (or only community-distinguishable) on the redirect, the plan's user-facing copy for `access_denied` has to cover both "you declined" and "your admin has to approve this" without claiming to know which happened; the AADSTS number in `error_description` can be logged to tell them apart after the fact, but never branched on.

### Gaps
- No Microsoft page states the OAuth `error` value delivered to the redirect_uri for scenarios 1, 2, 3, or 5 (the consent-blocked/"Need admin approval" family). Searched: auth-code-flow, OIDC, troubleshoot-consent-issues, admin-consent-workflow overview + configure pages, risk-based step-up, publisher verification. The documented material stops at the interrupt screen.
- Whether submitting an approval request (scenario 2) produces a different redirect than cancelling the same screen (scenario 3) is not documented anywhere found; community evidence shows the same `access_denied`/`error_subcode=cancel` shape for both.

## Key question 2 — Does Microsoft document `suberror`/`error_subcode` on authorization-endpoint redirects? What is the documented redirect response shape?

### Takeaway
No. The documented authorization-endpoint redirect carries exactly `error` and `error_description` (plus the echoed `state`); `error_codes`, `timestamp`, `trace_id`, `correlation_id` and `error_uri` are documented only on the token-endpoint JSON body. Neither `suberror` nor `error_subcode` appears in any Entra identity-platform reference page found — `error_subcode=cancel` is observable in the wild and in community posts but is undocumented, so the plan must not rely on it.

### Cited Findings
- The documented redirect shape, in full: "Error responses may also be sent to the redirect_uri so the app can handle them appropriately:" example `GET http://localhost? error=access_denied &error_description=the+user+canceled+the+authentication`; parameter table: "`error` | An error code string that can be used to classify types of errors, and to react to errors. This part of the error is provided so that the app can react appropriately to the error, but doesn't explain in depth why an error occurred." and "`error_description` | A specific error message that can help a developer identify the cause of an authentication error. This part of the error contains most of the useful information about why the error occurred." — [v2-oauth2-auth-code-flow, § Error response](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow). No other parameters are documented for the redirect.
- `state` is echoed on success responses: "`state` | If a state parameter is included in the request, the same value should appear in the response. The app should verify that the state values in the request and response are identical." — [v2-oauth2-auth-code-flow, successful-response table](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow); the `/adminconsent` endpoint documents `state` on its error response explicitly — [v2-admin-consent, § Error response](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent).
- The richer structure is token-endpoint JSON only. Token error example on the same page: `{"error": "invalid_scope", "error_description": "AADSTS70011: ... Trace ID: ... Correlation ID: ... Timestamp: ...", "error_codes": [70011], ...}` with the field table "`error_codes` | A list of STS-specific error codes that can help in diagnostics." — [v2-oauth2-auth-code-flow, § Error response (token)](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow). The reference-error-codes page shows the same JSON shape including `"error_uri":"https://login.microsoftonline.com/error?code=70011"` — [reference-error-codes, § Handling error codes in your application](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes).
- `suberror` / `error_subcode`: zero occurrences in the raw HTML of v2-oauth2-auth-code-flow, v2-protocols-oidc, reference-error-codes, v2-admin-consent, and the MSAL.NET error-handling page ([Handle errors and exceptions in MSAL.NET](https://learn.microsoft.com/en-us/entra/msal/dotnet/advanced/exceptions/msal-error-handling), ms.date 2024-06-04) — each page downloaded in full and grepped. Two targeted web searches for "error_subcode" and "suberror" on learn.microsoft.com returned only the error-codes reference (which does not contain either term) and community Q&A posts.

### Inferences
- Classification logic should read `error` and `state` from the redirect, keep `error_description` strictly for logs, and treat any extra parameters (`error_subcode`, `admin_consent`, `error_uri` if ever present) as unspecified: safe to log verbatim, never to branch on.

### Gaps
- Could not find any Microsoft reference defining `suberror` even for the token endpoint of the standard v2 /token endpoint (it shows up in community-posted token-response examples, e.g. a Q&A answer with `"suberror": "basic_action"`, and in some product-specific docs, but no identity-platform reference page found defines it). A guess at a native-auth error reference URL (`reference-native-auth-api-oauth2-errors`) returned 404; the exact slug, if such a page exists, was not located.

## Key question 4 — Does any Microsoft page map AADSTS codes to the OAuth `error` values they accompany on the redirect, and what is Microsoft's classification rule?

### Takeaway
No mapping table exists anywhere found. Microsoft's explicit, quotable rule is the opposite: the AADSTS reference "should never be used by the client itself" and "Apps that take a dependency on text or error code numbers will be broken over time"; the client-side contract is the OAuth `error` portion alone. The only documented pairing of an AADSTS number with a redirect `error` value anywhere in the identity-platform docs is the `/adminconsent` endpoint example (`error=consent_required` carrying `AADSTS65004` in its description).

### Cited Findings
- The rule, verbatim: "This documentation is provided for developer and admin guidance, but should never be used by the client itself. Error codes are subject to change at any time in order to provide more granular error messages that are intended to help the developer while building their application. Apps that take a dependency on text or error code numbers will be broken over time." — [reference-error-codes](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes) (ms.date 2025-02-03)
- What to classify on instead, verbatim: "The OAuth2.0 spec provides guidance on how to handle errors during authentication using the error portion of the error response." — [reference-error-codes, § Handling error codes in your application](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes); reinforced by the redirect parameter definition "An error code string that can be used to classify types of errors, and to react to errors." — [v2-oauth2-auth-code-flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- The one documented pairing: `/adminconsent` decline → `&error=consent_required &error_description=AADSTS65004%3a+The+resource+owner+or+authorization+server+denied+the+request...` — [v2-admin-consent, § Error response](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)
- AADSTS numbers reach a redirect only embedded inside `error_description` free text (as in the `/adminconsent` example above); the redirect shape has no `error_codes` array — that field is documented only on token-endpoint JSON ("`error_codes` | A list of STS-specific error codes that can help in diagnostics.") — [v2-oauth2-auth-code-flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

### Inferences
- For the engineering plan: branch on `error` ∈ {`access_denied`, `interaction_required`, `login_required`, `consent_required`} plus a catch-all for the protocol/dev errors; regex-extract `AADSTS\d+` from `error_description` for structured logging only. This is exactly the posture Microsoft's own wording licenses and nothing more.

### Gaps
- No Microsoft page maps AADSTS codes to the OAuth `error` values they ride with; the absence is the finding. Any such mapping an engineer builds from logs is observational and version-fragile by Microsoft's own statement above.
