## `prompt=none` semantics on the v2 authorize endpoint, and the documented error values

### Takeaway
`prompt=none` guarantees no interactive UI; if the request cannot complete silently via SSO the authorize endpoint returns an error at the redirect URI. The auth-code-flow page documents exactly two silent-failure error codes on the **authorize** endpoint: `login_required` (no single signed-in user could be resolved) and `interaction_required` ("Another authentication step or consent is required"). `consent_required` is documented only in the **token**-endpoint error table on that page, where the page itself notes it is non-standard there and normally an authorize-endpoint code per OIDC — so a robust client should treat `interaction_required`, `login_required`, and `consent_required` as the family of "interaction needed" codes, but the two Microsoft documents checked only enumerate the first two for the authorize response.

### Cited Findings
- `prompt` parameter, full documented semantics: "Indicates the type of user interaction that is required. Valid values are `login`, `none`, `consent`, and `select_account`.- `prompt=login` forces the user to enter their credentials on that request, negating single-sign on.- `prompt=none` is the opposite. It ensures that the user isn't presented with any interactive prompt. If the request can't be completed silently by using single-sign on, the Microsoft identity platform returns an `interaction_required` error.- `prompt=consent` triggers the OAuth consent dialog after the user signs in, asking the user to grant permissions to the app.- `prompt=select_account` interrupts single sign-on providing account selection experience listing all the accounts either in session or any remembered account or an option to choose to use a different account altogether." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- Authorize-endpoint error table, `login_required` row — Description: "Too many or no users found." Client Action: "The client requested silent authentication (`prompt=none`), but a single user couldn't be found. This error may mean there are multiple users active in the session, or no users. This error takes into account the tenant chosen. For example, if there are two Microsoft Entra accounts active and one Microsoft account, and `consumers` is chosen, silent authentication works." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- Authorize-endpoint error table, `interaction_required` row — Description: "The request requires user interaction." Client Action: "Another authentication step or consent is required. Retry the request without `prompt=none`." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- `consent_required` appears only in the **token endpoint** error table on that page: "The request requires user consent. This error is non-standard. It's usually only returned on the `/authorize` endpoint per OIDC specifications. Returned when a `scope` parameter was used on the code redemption flow that the client app doesn't have permission to request." Client action: "The client should send the user back to the `/authorize` endpoint with the correct scope to trigger consent." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- Error responses are delivered to the app's redirect URI, not thrown at the browser: "Error responses may also be sent to the `redirect_uri` so the app can handle them appropriately" (example shows `error=...&error_description=...` as query parameters) — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- The OIDC protocol page's own "Error codes for authorization endpoint errors" table lists only `invalid_request`, `unauthorized_client`, `access_denied`, `unsupported_response_type`, `server_error`, `temporarily_unavailable`, `invalid_resource` — it does not enumerate `login_required`/`interaction_required`/`consent_required` at all; its prompt paragraph says only "the Microsoft identity platform returns an error" without naming the code. — [OIDC protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc)

### Inferences
- For a parked-onboarding "has consent arrived yet?" probe, the app should branch on the `error` query parameter at its redirect URI: `login_required` → no usable Microsoft session in this browser (says nothing about consent); `interaction_required`/`consent_required` → a session exists but sign-in or consent UI is needed; a `code` → silent success, consent and session both exist. Microsoft's documented client action for `interaction_required` ("Retry the request without `prompt=none`") is exactly the resume path: fall back to an interactive authorize request.
- Because the error arrives as a redirect to the app's own `redirect_uri`, the probe must run in the user's browser (a full-page or top-level navigation from the app); it is not a server-side API call.

### Gaps
- Microsoft's v2 pages do not document `consent_required` in the authorize-endpoint error table (only the token-endpoint table, with a note that per OIDC it usually belongs to `/authorize`). Whether the live authorize endpoint emits `consent_required` vs `interaction_required` when a session exists but consent does not: NOT CONFIRMED from the two protocol pages checked; the only authorize-endpoint promise in writing is `interaction_required`.

## Does `prompt=none` require an existing Microsoft session? How does `login_hint` interact with it?

### Takeaway
Yes. `prompt=none` rides on single sign-on: with no signed-in user in the browser the request fails (documented cause "no signed-in user", surfacing as `login_required`, whose description is "Too many or no users found"), regardless of whether tenant-wide consent exists. Microsoft explicitly says `prompt=none` "should be paired with a `login_hint`" to disambiguate which user must be signed in; the hint does not create a session, it only selects among existing ones.

### Cited Findings
- "The `prompt=none` parameter is the opposite, and should be paired with a `login_hint` to indicate which user must be signed in. These parameters ensure that the user isn't presented with any interactive prompt at all. If the request can't be completed silently via single sign-on, the Microsoft identity platform returns an error. Causes include no signed-in user, the hinted user isn't signed in, or multiple users are signed in but no hint was provided." — [OIDC protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc)
- `login_required` description/action (again): "Too many or no users found." / "The client requested silent authentication (`prompt=none`), but a single user couldn't be found. This error may mean there are multiple users active in the session, or no users." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- `login_hint` documented purpose: "You can use this parameter to pre-fill the username and email address field of the sign-in page for the user. Apps can use this parameter during reauthentication, after already extracting the `login_hint` [optional claim] from an earlier sign-in." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- Default behavior with no `prompt` at all: "The default behavior is to either sign in the sole current user, show the account picker if there are multiple users, or show the login page if there are no users signed in." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- Constraint: "You can't use both `login_hint` and `select_account`." — [OIDC protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc)

### Inferences
- A `prompt=none` probe is a "session AND consent" test, not a consent test. A `login_required` result after the admin granted consent out of band means only that this browser has no (matching) Microsoft session — the parked onboarding must not interpret it as "consent still missing."
- Consequently a `prompt=none` probe cannot be fired blind on page load as a consent detector for a signed-out owner; it is useful when the owner is plausibly SSO-signed-in (e.g. they just came back from the admin-consent redirect, which required an admin sign-in at Microsoft in that same browser). Passing `login_hint` (captured from a prior sign-in's claim) plus the tenant ID in the authority path makes the silent attempt deterministic about *which* session it tests.

### Gaps
- None. The documented behavior fully answers the question.

## The other `prompt` values — and does `prompt=consent` force the dialog even when tenant-wide admin consent exists?

### Takeaway
`prompt=login` forces credential entry (breaks SSO); `prompt=select_account` forces the account picker; `prompt=consent` "triggers the OAuth consent dialog after the user signs in" — and the `.default` documentation states that supplying `prompt=consent` shows the consent prompt for all required permissions even when a grant already exists, so it must never be used on the post-admin-consent resume path (and may even fail outright for a non-admin user if the permissions are admin-restricted).

### Cited Findings
- `prompt=login`: "forces the user to enter their credentials on that request, negating single-sign on." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- `prompt=select_account`: "interrupts single sign-on providing account selection experience listing all the accounts either in session or any remembered account or an option to choose to use a different account altogether." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- `prompt=consent`: "triggers the OAuth consent dialog after the user signs in, asking the user to grant permissions to the app." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- Explicit confirmation that `prompt=consent` overrides existing consent (in the `.default` section, which generalizes the consent-check logic): "If consent exists, the returned token contains all scopes granted for that resource for the signed-in user. However, if no permission was granted for the requested resource (or if the `prompt=consent` parameter is provided), a consent prompt is shown for all required permissions configured on the client application registration, for all APIs in the list." — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- Worked example of forcing consent despite an existing grant: "The client then initiates a second sign-in using `scope=https://graph.microsoft.com/.default`, and this time forces consent using `prompt=consent`. If the user is allowed to consent for all the permissions that the application registered, they're shown the consent prompt. (If not, they're shown an error message or the [admin consent request] form.)" — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- The ordinary (no-`prompt`) consent check: "At this point, the user is asked to enter their credentials and complete the authentication. The Microsoft identity platform also ensures that the user has consented to the permissions indicated in the `scope` query parameter. If the user hasn't consented to any of those permissions, it asks the user to consent to the required permissions." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

### Inferences
- The Google-style pattern "always send prompt=consent on reconnect" is actively harmful on Entra: it re-surfaces the consent dialog the admin consent was supposed to remove, and for admin-restricted permissions a non-admin owner hitting that forced prompt gets an error or the "Approval required" form instead of a token.
- The correct Entra resume request after admin consent is an ordinary authorize request with no `prompt` (or `prompt=none` for the silent probe), letting the platform's own consent check find the tenant-wide grant and skip the dialog.

### Gaps
- None.

## Refresh token issuance: is `offline_access` in scope sufficient, without `prompt=consent`?

### Takeaway
Yes. On the v2 endpoint a refresh token is returned from the token endpoint whenever (and only when) `offline_access` was requested; no documented condition involves `prompt=consent`. Microsoft additionally documents that `offline_access` is implicitly granted whenever any delegated permission is granted, so a tenant-wide grant of `Calendars.ReadWrite` carries `offline_access` with it.

### Cited Findings
- Token response, `refresh_token` parameter: "An OAuth 2.0 refresh token. The app can use this token to acquire other access tokens after the current access token expires. Refresh tokens are long-lived. They can maintain access to resources for extended periods. ... **Note:** Only provided if `offline_access` scope was requested." — [Auth code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)
- "On the Microsoft identity platform (requests made to the v2.0 endpoint), your app must explicitly request the `offline_access` scope, to receive refresh tokens." — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- "If any delegated permission is granted, offline_access is implicitly granted. You can assume that the application has offline_access if there are any delegated permissions granted." — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- Consent-page presentation of `offline_access`: "On the consent page, this scope appears as the **Maintain access to data you have given it access to** permission." — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- General issuance statement: "A refresh token is used to obtain new access and refresh token pairs when the current access token expires. When a client acquires an access token to access a protected resource, the client also receives a refresh token." — [Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)
- Troubleshooting list for a missing refresh token names only scope, grant type, and client configuration — not `prompt`: "**Scope requirements**: Ensure that you're requesting the `offline_access` scopes along with any other necessary scopes. **Authorization grant type**: The refresh token is provided when using the authorization code grant type. ... **Client configuration**: Check your application's settings in the identity platform. Certain configurations may restrict the issuance of refresh_tokens." — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- Lifetime for a confidential web app: "**90 days for** all other scenarios" (24 hours applies to SPAs and email-OTP flows only); "Refresh tokens replace themselves with a fresh token upon every use." Revocation table: for "Confidential client token", password change/expiry/SSPR leave the token "Stays alive"; it is revoked on "Admin resets password (Microsoft Entra admin center)", "User revokes their refresh tokens", and "Admin revokes all refresh tokens for a user". — [Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)
- Refresh tokens are not resource-bound: "Refresh tokens are bound to a combination of user and client, but aren't tied to a resource or tenant. A client can use a refresh token to acquire access tokens across any combination of resource and tenant where it has permission to do so." — [Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)

### Inferences
- Unlike Google (where a refresh token is minted only on a consent-approved authorization, so `prompt=consent` is the reconnect idiom), Entra mints a refresh token on every auth-code redemption that included `offline_access` — including a fully silent `prompt=none` one. The silent probe that confirms consent therefore *also* completes the connection: redeem the code it returns and the app holds the long-lived refresh token, no extra prompt of any kind.

### Gaps
- None.

## Is there a documented server-to-server way for the vendor to check whether its grants now exist in the customer tenant?

### Takeaway
No. The documented programmatic read of delegated-permission grants is Microsoft Graph `GET /oauth2PermissionGrants`, and its permissions table requires a token for the *customer* tenant (`Directory.Read.All` least-privileged, delegated or application) — credentials the vendor only has after the customer tenant has already consented to something. Microsoft documents no anonymous or vendor-side query of another tenant's consent state. The two documented signals a vendor can receive are both browser-borne: the admin-consent endpoint's redirect back (`admin_consent=True&tenant=...&scope=...`) and the outcome of an authorize request (`prompt=none` probe or interactive sign-in).

### Cited Findings
- What the Graph API returns: "Retrieve a list of oAuth2PermissionGrant objects, representing delegated permissions which have been granted for client applications to access APIs on behalf of signed-in users." — [List oAuth2PermissionGrants](https://learn.microsoft.com/en-us/graph/api/oauth2permissiongrant-list)
- Its permissions table: "Delegated (work or school account): Directory.Read.All ... Application: Directory.Read.All" (higher: DelegatedPermissionGrant.ReadWrite.All, Directory.ReadWrite.All); "For delegated access using work or school accounts, the signed-in user must be assigned a supported Microsoft Entra role". — [List oAuth2PermissionGrants](https://learn.microsoft.com/en-us/graph/api/oauth2permissiongrant-list)
- Tenant-wide grants are verified with exactly this API in Microsoft's own how-to (run by the customer's admin, not the vendor): "Confirm that you've granted tenant wide admin consent by running the following request. `GET https://graph.microsoft.com/v1.0/oauth2PermissionGrants?$filter=clientId eq '...' and consentType eq 'AllPrincipals'`" — [Grant tenant-wide admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)
- The admin-consent endpoint's success response, delivered to the vendor's redirect URI: "`?admin_consent=True &tenant=aaaabbbb-0000-cccc-1111-dddd2222eeee &scope=... &state=12345`" with `tenant` described as "The directory tenant that granted your application the permissions it requested, in GUID format." and `admin_consent` as "Will be set to `True`." — [Admin consent endpoint](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)
- That redirect must not be trusted as authentication: "Warning — Never use the **tenant ID** value of the `tenant` parameter to authenticate or authorize users. The tenant ID value can be updated and sent by bad actors to impersonate a response to your app. This can cause your application to be exposed to security incidents." — [Admin consent endpoint](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)
- The admin-consent *error* redirect also carries `admin_consent=True` (it only flags the flow, not success): "`admin_consent` — Will be set to `True` to indicate that this response occurred on an admin consent flow." with `error`/`error_description` alongside (example: `error=consent_required`, `AADSTS65004 ... denied the request`). — [Admin consent endpoint](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)
- Freshly written grants may lag on read: "This request might have replication delays for delegated permission grants that were recently created, updated, or deleted. This delay will be minimized if a filter on `clientId` is specified." — [List oAuth2PermissionGrants](https://learn.microsoft.com/en-us/graph/api/oauth2permissiongrant-list)
- Grants written via Graph take effect without review: "Be careful! Permissions granted programmatically aren't subject to review or confirmation. They take effect immediately." — [Grant tenant-wide admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)

### Inferences
- There is a chicken-and-egg: calling Graph in the customer tenant requires a grant in the customer tenant, so "poll Graph until consent appears" is not available to the vendor unless the vendor also holds (admin-consented) `Directory.Read.All` application permission there — which is a far heavier ask than `Calendars.ReadWrite` and out of scope here. Plainly: **with only delegated Calendars.ReadWrite + offline_access, the vendor has no server-to-server, no-user-present way to ask Microsoft "has the admin consented yet?"** The check has to ride a browser: either the admin-consent redirect landing back on the vendor's `redirect_uri`, or a (silent or interactive) authorize attempt by the returning user.
- Since the admin-consent redirect is spoofable (the Warning above) and the error redirect also says `admin_consent=True`, the redirect should only *unpark* the onboarding optimistically; the authoritative confirmation is a successful authorize → token redemption (a real `code` exchanged with the client secret), which cannot be forged.

### Gaps
- No Microsoft page was found documenting any vendor-side (home-tenant-credentialed) API over another tenant's service principals or grants; I am reporting that absence as the answer rather than from an explicit "this does not exist" statement — Microsoft does not publish such a negative. NOT CONFIRMED beyond absence of documentation.

## After tenant-wide admin consent: what do subsequent user sign-ins look like? Any residual first-sign-in prompt?

### Takeaway
Microsoft states directly that after admin consent on behalf of the organization, users are not prompted for consent for that application — with one documented exception: the user can still be prompted "if an application requests another permission that the administrator hasn't granted." No Microsoft page found documents a residual first-sign-in consent prompt for `openid`/`profile` specifically when those scopes were covered by the admin grant; the safe reading is that the exception clause governs: whatever the sign-in request asks for that the grant does not cover will prompt.

### Cited Findings
- "After an administrator grants admin consent on behalf of the organization, users aren't prompted for consent for that application. In certain cases, a user might be prompted for consent even after an administrator grants consent. An example might be if an application requests another permission that the administrator hasn't granted." — [User and admin consent overview](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/user-admin-consent-overview)
- The grant how-to's own description line: "Learn how to grant tenant-wide consent to an application so that end-users aren't prompted for consent when signing in to an application." — [Grant tenant-wide admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)
- "By default, granting tenant-wide admin consent to an application allows all users to access the application unless otherwise restricted." — [Grant tenant-wide admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)
- Caveat on re-granting: "Important — Granting tenant-wide admin consent may revoke permissions that have already been granted tenant-wide for that application. Permissions that users have already granted on their own behalf aren't affected." — [Grant tenant-wide admin consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)
- The consent check at sign-in is grant-aware, not per-user-prompt-always: "User consent happens when a user attempts to sign into an application. The user provides their sign-in credentials, which are checked to determine if consent already is granted. If no previous record of user or admin consent for the required permissions exists, the user is shown a consent prompt". — [Permissions & consent overview](https://learn.microsoft.com/en-us/entra/identity-platform/permissions-consent-overview)
- The admin consent endpoint can cover the OIDC scopes in the same grant: `scope` "Defines the set of permissions being requested by the application. This can be either static (using `/.default`) or dynamic scopes. This can include the OIDC scopes (`openid`, `profile`, `email`)." — [Admin consent endpoint](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)
- With `/.default`: "If you've used a static (`/.default`) value, it will function like the v1.0 admin consent endpoint and request consent for all scopes found in the required permissions (both user and app)." — [Admin consent endpoint](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)
- `.default` sign-in after a grant exists: "If the client requests `scope=https://graph.microsoft.com/.default`, no consent prompt is shown, regardless of the contents of the client application's registered permissions for Microsoft Graph. The returned token contains the scopes `Mail.Read` and `User.Read`." (Example 1, "The user, or tenant admin, has granted permissions") — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- "The `.default` scope parameter only triggers a consent prompt if consent wasn't granted for any delegated permission between the client and the resource, on behalf of the signed-in user." — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)
- How the OIDC scopes render when a prompt does appear: "The `openid` scope appears on the work account consent page as the **Sign you in** permission." and (offline_access note) "This permission currently appears on all consent pages, even for flows that don't provide a refresh token". — [Scopes/OIDC](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)

### Inferences
- To make the post-consent sign-in genuinely prompt-free, the admin-consent request the app constructs should cover every scope its later authorize requests will send — i.e. include `openid profile offline_access` (or use `/.default` with those among the registered required permissions) alongside `Calendars.ReadWrite`. If the admin grant covers only `Calendars.ReadWrite` and the sign-in then dynamically requests `openid profile`, the documented exception ("requests another permission that the administrator hasn't granted") is the clause that would trigger a prompt.
- Recommended resume shape consistent with every quote above: (1) admin consent granted out of band → tenant-wide `oauth2PermissionGrant` with `consentType: AllPrincipals` exists; (2) when the owner returns (or lands on the vendor's redirect from the consent flow), the app issues a normal authorize request — tenant-pinned authority, `prompt=none` + `login_hint` if it wants to avoid any UI, or no `prompt` if a sign-in screen is acceptable; (3) consent check finds the tenant-wide grant, no consent dialog; (4) code redeemed with `offline_access` in scope → access + refresh token. No `prompt=consent` anywhere.

### Gaps
- Whether a user who has *never* signed in to the app sees any non-consent, first-sign-in interstitial (e.g. app access panel or MFA registration) after admin consent: not covered by the pages checked; those are tenant policy surfaces, not consent. NOT CONFIRMED either way.
- An explicit Microsoft statement that `openid`/`profile` are (or are not) auto-covered by a portal "Grant admin consent" click: the portal path consents to "the permissions that the application requires" (its configured/required permissions), and `openid`/`profile` are grantable scopes that can be listed there and appear in real `AllPrincipals` grants (the Graph example response includes "openid profile" in an `AllPrincipals` scope string — [List oAuth2PermissionGrants](https://learn.microsoft.com/en-us/graph/api/oauth2permissiongrant-list)), but no page states the portal button always includes them. NOT CONFIRMED; the safe design is to put them in the app registration's required permissions and/or the adminconsent `scope`.
