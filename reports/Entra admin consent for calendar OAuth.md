# Branch on error, trust only redeemed codes

Microsoft gives a multi-tenant SaaS app exactly one signal it is licensed to branch on along the user authorize/callback path — the OAuth **`error` query parameter**, whose authorize-endpoint vocabulary is a closed nine-value table — and exactly one signal that is authoritative proof of a working connection anywhere in the system: **an authorization code redeemed server-side with the client secret**. Everything else is weaker than it looks. The **`/adminconsent` endpoint records a tenant-wide grant and returns no code and no token** — its success redirect carries only `admin_consent=True`, `tenant`, `scope`, `state`, its *error* redirect carries `admin_consent=True` too, and Microsoft explicitly warns the returned `tenant` value is forgeable ([v2-admin-consent](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)). The admin consent workflow's request expiry is a tenant-admin setting (`requestDurationInDays`) for which **no primary Microsoft source states a range or default**; the vendor cannot see it, and with only delegated `Calendars.ReadWrite` + `offline_access` the vendor has **no server-to-server way to ask Microsoft whether consent has arrived** — every signal rides a browser redirect. The sharpest documentation hole sits exactly where this product lives: Microsoft documents the "Need admin approval" interrupt screens and their AADSTS codes, but **publishes no statement of what reaches the `redirect_uri` when the user exits those screens** — community evidence points to `error=access_denied` with an undocumented `error_subcode=cancel`, and that is NOT CONFIRMED by any Microsoft page. This matters because the earlier report established that the blocked path is the *normal* path: Microsoft's managed consent policy, the default for new tenants, excludes every calendar scope from end-user consent ([Manage app consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies)). The fail-closed gate therefore reduces to four rules: a redirect without a `code` is a failure; `access_denied` (and kin) parks the tenant with copy that covers both "you declined" and "your admin must approve"; `/adminconsent`'s redirect may *optimistically* unpark but never verifies; and payment follows only a fresh authorization-code round trip that returned a refresh token.

## The authorize redirect speaks nine words, and the loudest scenario is unwritten

Microsoft documents the `/authorize` redirect error vocabulary as a closed table: `invalid_request`, `unauthorized_client`, `access_denied`, `unsupported_response_type`, `server_error`, `temporarily_unavailable`, `invalid_resource`, `login_required`, `interaction_required` ([v2-oauth2-auth-code-flow, § Error codes for authorization endpoint errors](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)). The documented redirect shape is exactly `error` + `error_description` (plus the echoed `state`) and nothing more; the richer structure — `error_codes`, `timestamp`, `trace_id`, `correlation_id`, `error_uri` — is documented only on token-endpoint JSON. **Neither `suberror` nor `error_subcode` appears in any Entra identity-platform reference page**: the full HTML of the auth-code-flow, OIDC, error-reference, admin-consent and MSAL.NET error pages was grepped with zero hits, so `error_subcode=cancel`, though real in the wild, is undocumented and must never be branched on.

Of the consent-failure scenarios the gate must handle, only two are classifiable from primary documentation. A plain user Cancel/Deny on an ordinary consent prompt is `access_denied` — Microsoft's own example redirect is literally `error=access_denied&error_description=the+user+canceled+the+authentication` ([v2-oauth2-auth-code-flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow); same example on [v2-protocols-oidc](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc)). And a `prompt=none` request before consent exists returns `interaction_required` ("Another authentication step or consent is required. Retry the request without prompt=none") or `login_required` when no single signed-in user is found ([v2-oauth2-auth-code-flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)). For the consent-blocked family — tenant policy blocks user consent with the workflow disabled; workflow enabled and the user submits a request; workflow enabled and the user cancels the screen; risk-based step-up blocking an unverified publisher — Microsoft documents the interrupt screens and their on-screen codes (AADSTS90094 "An administrator ... has set a policy that prevents you from granting ... the permissions it is requesting", [Troubleshoot consent issues](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshoot-consent-issues); the step-up variant on [Configure risk-based step-up consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-risk-based-step-up-consent)), **but no Microsoft page states which OAuth `error` value reaches the `redirect_uri` when the user exits those screens — NOT CONFIRMED from primary docs.** The closest primary statement covers only the workflow's "Back to app" button: after a user submits an admin consent request, "Microsoft Entra ID sends an AADSTS65004 error to the redirect URI specified in the original authentication request. This error is an expected part of the admin consent workflow" ([application-sign-in-unexpected-user-consent-error](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/application-sign-in-unexpected-user-consent-error)) — it names the AADSTS code, not the OAuth `error` parameter that carries it. Community evidence (a Microsoft Q&A thread — user-posted content, not documentation) shows the interrupt arriving as `error=access_denied&error_subcode=cancel&...&error_description=AADSTS65004...` ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2237594/how-to-handle-admin-consent-in-oauth-flow)), and whether submitting a request produces a different redirect than cancelling the same screen is documented nowhere.

Microsoft's own classification rule settles how to build despite the hole. The AADSTS reference states: "This documentation is provided for developer and admin guidance, but **should never be used by the client itself**. ... Apps that take a dependency on text or error code numbers will be broken over time," and directs clients to "the error portion of the error response" ([reference-error-codes](https://learn.microsoft.com/en-us/entra/identity-platform/reference-error-codes)). No Microsoft page maps AADSTS codes to the OAuth `error` values they ride with — the absence is the finding. The reference page itself (downloaded complete, 370 rows) carries AADSTS65001 (`DelegationDoesNotExist`), AADSTS65004 (`UserDeclinedConsent`), AADSTS90094 (`AdminConsentRequired`) and AADSTS90095 (`AdminConsentRequiredRequestAccess`), but **AADSTS900941 and AADSTS900942 are absent from it entirely** — the table jumps from 90099 to 900971. AADSTS900941 (`AdminConsentRequiredDueToRiskyApp`) is documented only on the troubleshooting page ([Troubleshoot consent issues](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshoot-consent-issues)); **AADSTS900942 was not found on any Microsoft page checked — NOT CONFIRMED that it exists at all** (if ever observed, resolve it live via `https://login.microsoftonline.com/error?code=900942`, the lookup the reference page itself prescribes). The engineering consequence: branch on `error` ∈ {`access_denied`} → park; {`interaction_required`, `login_required`, `consent_required`} → send through interactive auth; anything else → protocol/dev failure, fail loud. Regex-extract `AADSTS\d+` from `error_description` for structured logging only, and write the `access_denied` operator copy to cover both "you declined" and "your admin has to approve this," because the redirect cannot tell those apart.

## /adminconsent records a grant and mints nothing

The gate-clearer model is confirmed by the documented contract. The v2 endpoint is `https://login.microsoftonline.com/{tenant}/v2.0/adminconsent` with required `client_id`, `redirect_uri`, `scope` and recommended `state`; the tenant segment takes a GUID, a domain name, or `organizations` — "Do not use 'common', as personal accounts cannot provide admin consent except in the context of a tenant. To ensure best compatibility ... use the tenant ID when possible" ([v2-admin-consent](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)). `scope` can be dynamic or `/.default` ("it will function like the v1.0 admin consent endpoint and request consent for all scopes found in the required permissions"), and can include the OIDC scopes; admin consent "requires the static permissions registered for the app," so `Calendars.ReadWrite`, `offline_access`, `openid` and `profile` all belong in the app registration's required-permissions list ([consent-types-developer](https://learn.microsoft.com/en-us/entra/identity-platform/consent-types-developer)). The `redirect_uri` "must exactly match one of the redirect URIs that you registered" — the same rule as `/authorize` — and Microsoft's own prerequisites anticipate a dedicated consent-callback URI separate from the code-bearing one ([auth-v2-service](https://learn.microsoft.com/en-us/graph/auth-v2-service)). Whether v2 tolerates the "additional path segments" the v1 page mentions is NOT CONFIRMED; build to the stricter v2 exact-match rule, on a `web`-typed URI.

Success is a browser GET to the `redirect_uri` carrying **exactly `admin_consent=True`, `tenant` (GUID), `scope`, and `state` — no authorization code, no access token, no refresh token for anyone**. What gets written is a tenant-wide grant: for delegated permissions an `oauth2PermissionGrant` with `consentType: AllPrincipals` ([grant-admin-consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent); [permissions-consent-overview](https://learn.microsoft.com/en-us/entra/identity-platform/permissions-consent-overview)). The developer guide then says "your application is granted the permissions it requested. Next, you can request a token for the resource you want" — and the token request it shows is an ordinary `grant_type=authorization_code` exchange, presupposing a normal `/authorize` sign-in ([consent-types-developer](https://learn.microsoft.com/en-us/entra/identity-platform/consent-types-developer)). No single sentence in current docs reads "the admin consent endpoint does not return tokens"; the confirmation is compositional — the documented response tables contain no token field, and the documented next step is a code exchange — and should be stated in the plan as such, not as a quotation. "Delegated access requires delegated permissions. Both the client and the user must be authorized separately to make the request" ([permissions-consent-overview](https://learn.microsoft.com/en-us/entra/identity-platform/permissions-consent-overview)): the owner still has to sign in afterwards for the app to mint calendar tokens.

Two traps in the failure contract. First, **the documented v2 error redirect also carries `admin_consent=True`** — Microsoft's own example is `?admin_consent=True&error=consent_required&error_description=AADSTS65004...&state=12345`, with `admin_consent` defined as "set to `True` to indicate that this response occurred on an admin consent flow" ([v2-admin-consent](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)). The callback must branch on the presence of `error` first; `admin_consent=True` alone proves nothing. Second, the error vocabulary is inconsistent across Microsoft's own pages: the protocol reference shows `consent_required`, the developer guide shows `error=permission_denied&error_description=The+admin+canceled+the+request` ([consent-types-developer](https://learn.microsoft.com/en-us/entra/identity-platform/consent-types-developer)), and community traffic shows `access_denied` with `error_subcode=cancel` ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2237594/how-to-handle-admin-consent-in-oauth-flow)) — no official page enumerates the complete set, so treat *any* non-empty `error` as failure with one fixed message. And the success redirect is explicitly untrustworthy as proof: "Never use the **tenant ID** value of the `tenant` parameter to authenticate or authorize users. The tenant ID value can be updated and sent by bad actors to impersonate a response to your app" ([v2-admin-consent](https://learn.microsoft.com/en-us/entra/identity-platform/v2-admin-consent)). Use `tenant` only as a lookup hint against the signed `state`; the authoritative record is the `tid` claim of a validated token from the owner's subsequent sign-in.

Who can click approve: Privileged Role Administrator for anything; Cloud Application Administrator, AI Administrator, or Application Administrator for anything *except* Microsoft Graph application permissions; or a suitable custom role ([grant-admin-consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)) — this product's delegated-only request sits inside the Cloud/App Administrator tier, and "Global Administrator" is notably absent from the current list. Once the grant exists, "users aren't prompted again unless consent is revoked or new permissions are added" ([consent-types-developer](https://learn.microsoft.com/en-us/entra/identity-platform/consent-types-developer)) — but "when you change the configured permissions, you must also repeat the admin consent process" ([auth-v2-service](https://learn.microsoft.com/en-us/graph/auth-v2-service)), and re-granting "may revoke permissions that have already been granted tenant-wide for that application" ([grant-admin-consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)). Tenant-wide consent to a *delegated* permission does not widen reach: the app still acts only as whoever signed in — the onboarding copy must say so, per the earlier report.

## The expiry window is admin-chosen, range undocumented, and invisible to the vendor

The workflow itself ships off: both portal docs describe a feature a Global Administrator must turn on ("You must be a Global Administrator to turn on the admin consent workflow" ... "It can take up to an hour for the workflow to become enabled," [Configure the admin consent workflow](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-admin-consent-workflow)), and the overview frames it as a capability an admin grants by "turning on the admin consent workflow" ([admin-consent-workflow-overview](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/admin-consent-workflow-overview)). **"Disabled by default" is a well-supported inference, not a quoted fact** — no Microsoft sentence says it verbatim, though the CIS M365 benchmark's control "Ensure the admin consent workflow is enabled" ([Tenable rendering of CIS M365 v3.1.0](https://tenable.com/audits/items/CIS_Microsoft_365_v3.1.0_E3_Level_1.audit:fe8bac07e37155e9828cdfa49a603f56), secondary) only makes sense if tenants commonly have it off. The common first-run experience on a managed-policy tenant is therefore the dead-end "Need admin approval" prompt — no request queue, no email — unless the owner *is* the admin.

On the expiry window the finding is an absence, and it must be preserved as one. Graph's `adminConsentRequestPolicy.requestDurationInDays` is documented in full as "Specifies the duration the request is active before it automatically expires if no decision is applied" — Int32, **no minimum, no maximum, no default**, in v1.0 and beta alike ([adminConsentRequestPolicy resource type](https://learn.microsoft.com/en-us/graph/api/resources/adminconsentrequestpolicy)); the portal doc's entire description is "**Consent request expires after (days)** - Specify how long requests stay valid" ([Configure the admin consent workflow](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-admin-consent-workflow)). **The circulated claim "configurable up to 365 days, commonly 7 or 30" is NOT CONFIRMED by any primary source**; the 30-day figure comes from hardening guidance — CIS and the Australian Signals Directorate both recommend 30 ([ASD Blueprint](https://blueprint.asd.gov.au/configuration/entra-id/applications/enterprise-applications/consent-and-permissions/admin-consent-settings/), secondary). The documented reference points are a 3-day window in the portal doc's reminder example, `"requestDurationInDays": 5` in the Graph update example ([Update adminConsentRequestPolicy](https://learn.microsoft.com/en-us/graph/api/adminconsentrequestpolicy-update)), and — strangest — `"requestDurationInDays": 0` in the GET example's live enabled policy, **whose semantics are documented nowhere** ([Get adminConsentRequestPolicy](https://learn.microsoft.com/en-us/graph/api/adminconsentrequestpolicy-get)); the PowerShell cmdlet's "Default value: 0" is an auto-generated Int32 placeholder, not a service default ([Update-MgPolicyAdminConsentRequestPolicy](https://learn.microsoft.com/en-us/powershell/module/microsoft.graph.identity.signins/update-mgpolicyadminconsentrequestpolicy)). There is also **no `expiryDateTime` on the request objects**: `userConsentRequest` carries only `createdDateTime`, `completedDateTime` and a `status` that can be `Initializing`, `InProgress`, `Expired`, or `Completed` ([userConsentRequest resource type](https://learn.microsoft.com/en-us/graph/api/resources/userconsentrequest)), so even a reader with tenant access must compute expiry from the policy.

What each party can observe. The requesting user gets email at every transition — "Requestors receive email notifications when: They submit a new request for access. Their request expires. Their request is denied or blocked. Their request is approved" ([admin-consent-workflow-overview](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/admin-consent-workflow-overview)) — *but* requester emails ride the reviewer toggle: "If this option is disabled, email notifications to the requesters when a request is made and reviewed are also disabled" ([Configure the admin consent workflow](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/configure-admin-consent-workflow)), so the vendor cannot assume the user was ever told of the approval; the vendor's own nudge surface is the only reliable resume prompt. The vendor observes nothing at all: reading the requests requires `ConsentRequest.Read.All` and reading the policy requires tenant-side permissions — credentials inside the *customer* tenant, which the vendor by definition lacks while parked — and Graph cannot even act on requests from either side: "there aren't any methods available to programmatically approve or deny a request" ([consentrequests-overview](https://learn.microsoft.com/en-us/graph/api/resources/consentrequests-overview)). An expired request is terminal — expired requests drop to a history-only tab, nothing revives them, and re-requesting is explicitly permitted after a deny ("Denying a request won't prevent users from requesting admin consent to the application again," [review-admin-consent-requests](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/review-admin-consent-requests)) — so **the vendor sizes its parked TTL blind and must make the parked state re-enterable rather than one-shot**. Two live-page contradictions are flagged rather than resolved: the configure doc says new reviewers "aren't able to act on existing or expired" requests while the more recently updated overview says they "can view and act on all pending" requests including pre-existing ones; and the configure doc says only Global Administrators approve Graph app-role requests while the grant doc's list leads with Privileged Role Administrator — neither touches this product's delegated-only case. One more reviewer action matters to the gate: **Block** "not only denies the current request but also prevents future requests for the same application ... Blocking a request creates a service principal object for the application in your tenant in a disabled state" ([review-admin-consent-requests](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/review-admin-consent-requests)) — a tenant that blocked the app will never unpark, and the app cannot distinguish that from a slow admin.

## Silent resume tests the session as much as the consent

`prompt=none` "ensures that the user isn't presented with any interactive prompt. If the request can't be completed silently by using single-sign on, the Microsoft identity platform returns an `interaction_required` error" ([v2-oauth2-auth-code-flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)); it "should be paired with a `login_hint`," and the failure causes are "no signed-in user, the hinted user isn't signed in, or multiple users are signed in but no hint was provided" ([v2-protocols-oidc](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc)). The probe is therefore a **session-AND-consent test, not a consent test**: `login_required` after the admin approved means only that this browser has no matching Microsoft session, and the parked onboarding must not read it as "consent still missing." Because the outcome arrives as a redirect to the app's own `redirect_uri`, the probe is a top-level browser navigation, never a server-side call — it is useful precisely when the owner is plausibly SSO-signed-in (for instance, immediately after landing back from the admin-consent redirect, which required an admin sign-in at Microsoft in that same browser), made deterministic with `login_hint` from a prior sign-in's claim plus the tenant GUID in the authority path. On the error vocabulary, one caveat to carry: the authorize-endpoint table promises only `interaction_required` and `login_required` for silent failures; `consent_required` appears on that page only in the *token*-endpoint table with the note that it is "usually only returned on the /authorize endpoint per OIDC specifications" — **whether the live authorize endpoint emits `consent_required` versus `interaction_required` when a session exists but consent does not is NOT CONFIRMED**, so the classifier should accept all three in the needs-interaction bucket.

The refresh-token conditions make the silent probe self-completing. A refresh token is "Only provided if `offline_access` scope was requested" ([v2-oauth2-auth-code-flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)); no documented condition involves `prompt=consent`, and "If any delegated permission is granted, offline_access is implicitly granted" ([scopes-oidc](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)). Unlike Google, where `prompt=consent` is the reconnect idiom because refresh tokens are minted only on consent-approved authorizations, **Entra mints a refresh token on every code redemption that included `offline_access` — including a fully silent `prompt=none` one**, so the probe that confirms consent also finishes the connection: redeem the code it returns and the app holds the long-lived token (90 days for confidential-client scenarios, self-replacing on every use, [refresh-tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)). Conversely, `prompt=consent` is actively harmful on the resume path: "if the `prompt=consent` parameter is provided, a consent prompt is shown for all required permissions ... for all APIs in the list" even when the grant exists ([scopes-oidc](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)) — it re-surfaces the dialog the admin consent was supposed to remove, and for admin-restricted calendar permissions a non-admin owner gets the error or the "Approval required" form instead of a token. The correct resume request carries no `prompt` at all (or `prompt=none` for the silent variant) and lets the platform's consent check find the `AllPrincipals` grant. To keep that sign-in genuinely prompt-free, the admin-consent request should cover every scope the later authorize request will send — `openid profile offline_access` alongside `Calendars.ReadWrite`, or `/.default` over a complete registered list — because "a user might be prompted for consent even after an administrator grants consent ... if an application requests another permission that the administrator hasn't granted" ([user-admin-consent-overview](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/user-admin-consent-overview)); whether a portal "Grant admin consent" click always covers `openid`/`profile` is NOT CONFIRMED, so put them in the registered required permissions.

No server-to-server check exists. The documented programmatic read of delegated grants is Graph `GET /oauth2PermissionGrants`, whose least-privileged permission is `Directory.Read.All` — a token *for the customer tenant*, which the vendor only holds after that tenant has already consented to something ([List oAuth2PermissionGrants](https://learn.microsoft.com/en-us/graph/api/oauth2permissiongrant-list)); Microsoft's own verification query (`$filter=clientId eq '...' and consentType eq 'AllPrincipals'`) is written for the customer's admin, not the vendor ([grant-admin-consent](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/grant-admin-consent)). **With only delegated `Calendars.ReadWrite` + `offline_access`, the vendor has no no-user-present way to ask Microsoft "has the admin consented yet?"** — Microsoft publishes no vendor-side query over another tenant's consent state, and this is reported as an absence of documentation rather than a quoted negative, because Microsoft states no such negative. The two signals the vendor can receive are both browser-borne: the `/adminconsent` redirect, and the outcome of an authorize attempt. After an out-of-band approval, nothing pushes a signal to the vendor and the in-flight attempt cannot be resumed — "the user needs to begin a new authentication process with the application" ([application-sign-in-unexpected-user-consent-error](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/application-sign-in-unexpected-user-consent-error)); no primary sentence narrates the retry moment itself (NOT CONFIRMED verbatim — assembled from approval-grants-consent plus consent-allows-all-users quotes). The unpark event is the owner coming back and completing the round trip.

## The gate, assembled: park on access_denied, verify by redemption

Mapped onto the fail-closed "verify every required connection before taking payment" design, the contract yields a small state machine with one invariant. The callback classifies **only** on `error`, exactly as Microsoft's rule licenses: a `code` → redeem it server-side with `offline_access` in scope; receipt of a refresh token is the sole event that marks the Microsoft connection verified and clears the gate toward payment. `error=access_denied` → park the tenant in `awaiting_admin_consent`, with copy covering both the decline and the approval-pending readings, logging the `AADSTS\d+` extracted from `error_description` (65004 vs 90094 vs 900941 tells the operator which it was after the fact — never the code which branch it takes). `interaction_required` / `login_required` / `consent_required` → route to interactive auth. Any other `error` → protocol failure, surfaced loudly. The `/adminconsent` leg is offered from the parked state with the tenant GUID in the path and the full scope set; its callback checks `error` first (because `admin_consent=True` rides the error redirect too), treats `tenant` as a hint keyed to signed `state`, and on apparent success does nothing more than invite the owner to sign in again — optimistic unpark, never verification. The parked record carries a blind TTL (nothing under ~30 days is justified by any primary source, and the tenant's own window is invisible; a CIS/ASD-hardened tenant expires requests at 30 days), is re-enterable on a fresh attempt, and its re-engagement nudges come from this product, since the approval email to the requester may be switched off tenant-side. A tenant whose admin pressed **Block** will sit in this state forever and is indistinguishable from a slow one — which is exactly why the state must expire into "ask the owner to talk to their admin or try again," not into a refund-generating paid account.

## Conclusion

The striking shape of this contract is that Microsoft's documentation hole and Microsoft's design rule are the same fact seen twice. The company does not document what reaches the `redirect_uri` when policy blocks consent — and it separately instructs that clients must never depend on anything finer than the OAuth `error` parameter. An app built to the rule is immune to the hole: it never needed to know whether the user submitted a request or cancelled the screen, because both land in the same parked state and both exit it the same way, by a fresh sign-in that only succeeds once the grant exists. The undocumented `error_subcode=cancel` and the unenumerated `/adminconsent` error vocabulary stop being risks the moment the classifier treats "anything but a code" as failure.

The deeper consequence for the onboarding design is that **verification and connection are the same operation on Entra**. Because a silently-obtained code redeems into a refresh token just like an interactive one, there is no separate "check" step to build — the cheapest possible probe (`prompt=none` + `login_hint` + tenant-pinned authority) is also the completing transaction, and everything weaker than it (`admin_consent=True`, the forgeable `tenant`, the approval email, the absence of an error) is a hint at best. Take payment on a stored refresh token obtained in that round trip, and on nothing else; every NOT CONFIRMED item in this report sits strictly on the hint side of that line, which is precisely where a fail-closed design can afford to leave it.
