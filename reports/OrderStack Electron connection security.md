# Electron offers Jeff tools, not OrderStack's proof

The research found **no evidence that OrderStack (getorderstack.com) uses Electron**, and it found no OrderStack security documentation either. The site could not be read from the research environment: fetches failed with a TLS handshake error, and a real Chrome browser showed an error page. The Internet Archive holds no snapshot of it. The only first-party fact obtained is DNS: www.getorderstack.com is a CNAME to orderstack-app.onrender.com, hosted on Render behind Cloudflare, and that origin returns "Not Found" at its root. OrderStack therefore cannot serve as a reference design for Jeff, and this report does not treat it as one. This is "not found," not "disproven." Independent of OrderStack, Electron can help on one side of the connection only. Its main process can present a client certificate, pin server certificates, hold a token in OS-backed storage, and (on macOS) use a Secure Enclave-bound WebAuthn credential. It cannot give a Railway container an identity, and it does not stop an attacker who already controls the Mac user account or the app's files. Railway confirmed in April 2026 that it issues no workload identity tokens to running services, so every option for GeekAPI and GeekRepository reduces to a secret the container holds, or an outbound IP. Hardware-backed keys (FIDO, Secure Enclave) can protect Jeff's own machine but not a container. A MAC address is not a usable identity over the internet: it exists only on the local network segment, so a remote server never sees the client's MAC, and it can be changed in software. That point is general networking knowledge, not a finding from the notes.

## Electron gives a client the primitives, and none of them is a finished feature

Electron's documentation exposes the pieces of an mutual-TLS client but names no first-class mTLS or pinning feature. The `select-client-certificate` event lets the app choose from the operating system's certificate list, and requests made by the main process through `net.fetch` fire it with a null `webContents`, so a main-process-only client can pick a certificate with no renderer involved ([Electron app docs](https://www.electronjs.org/docs/latest/api/app)). The certificate comes from the OS or Chromium store, not from an app-managed key, so whether the key can be non-exportable depends on how the OS imported it, which the Electron docs do not cover. Pinning has to be hand-built in `ses.setCertificateVerifyProc`, where the callback can return `-2` to reject and `-3` to defer to Chromium. Returning `0` accepts but disables Certificate Transparency checks, and the result is cached by the network service ([session docs](https://www.electronjs.org/docs/latest/api/session)). The pinning recipe itself is inference: the docs give none. Linux smart-card client certificates have had open problems (issues [#20575](https://github.com/electron/electron/issues/20575) and [#32668](https://github.com/electron/electron/issues/32668), both closed, resolution unread), which does not affect a Mac but matters if any operator uses Linux.

For storing a token, `safeStorage` uses the macOS Keychain, which protects content from other users and from other apps, whereas Windows DPAPI protects only against other users, "but not against other apps in the same userspace." On Linux it can silently fall back to a hardcoded password when no secret store exists, detectable through `getSelectedStorageBackend()` returning `basic_text`. The synchronous API is deprecated and scheduled for removal in Electron 46 ([safeStorage docs](https://www.electronjs.org/docs/latest/api/safe-storage)). The only official hardware-backed route is `app.configureWebAuthn` on macOS, which binds credentials to the Secure Enclave through the Keychain and needs a `keychain-access-groups` entitlement. It serves WebAuthn from a renderer to a relying party, and the notes found no Electron-documented TPM, Windows Hello or Linux equivalent ([app docs, main branch](https://raw.githubusercontent.com/electron/electron/main/docs/api/app.md)). The release that introduced it is unconfirmed; the docs history points to PR #51563, and one search result attributes it to 41.5.0 (an unconfirmed attribution). The latest release at fetch time was v45.4.1.

The hardening settings protect the app's own code, which is where the pins and certificate-selection logic live. Context isolation (default since Electron 12) and the sandbox (default since Electron 20) are on by default. The security checklist requires HTTPS or WSS, IPC sender validation, and narrow preload APIs ([security tutorial](https://www.electronjs.org/docs/latest/tutorial/security)). ASAR integrity makes the app terminate on a header mismatch, but it can be bypassed unless `onlyLoadAppFromAsar` is also enabled ([ASAR integrity](https://www.electronjs.org/docs/latest/tutorial/asar-integrity)). By default the `RunAsNode` fuse, the `NODE_OPTIONS` fuse and `--inspect` remain enabled ([fuses](https://www.electronjs.org/docs/latest/tutorial/fuses)). Electron's documented update path, Squirrel, requires a signed app on macOS, but the docs say little about how update payloads are verified ([updates](https://www.electronjs.org/docs/latest/tutorial/updates)).

The limit is stated plainly in the notes. A malicious npm dependency or anyone running as the user can call `safeStorage.decryptString`, hook the certificate event, or override the verify procedure, and Electron publishes no threat model that rules this out. Third-party reports describe attackers tampering with ASAR archives for persistence and credential theft ([Atos](https://atos.net/en/lp/cybershield/asar-archives-an-overlooked-blind-spot); [Schneier](https://www.schneier.com/?p=12176), a secondary summary). Client-side measures raise the cost of an attack but leave the secret on the device, so the compensating design is server-side: short-lived tokens, revocation and rate limits. Those server-side controls are the notes' inference, not Electron documentation.

## Four device-identity options compared, with the Railway constraint decisive

Railway's reply on 2026-04-29 was: "We do not currently provide workload identity OIDC tokens to running services." Its only OIDC is "Login with Railway," a user-facing OAuth flow ([Railway Station](https://station.railway.com/questions/does-railway-provide-workload-oidc-token-67d87e3d)). That reply is a forum post, and Railway's variables documentation was not checked for anything newer. The consequence is that GeekAPI and GeekRepository can prove who they are only through something stored in their environment variables, which anyone with access to the Railway project can read. The options differ in what that secret is and in how much each protects Jeff's Mac and the Hostinger VPS.

**Client certificates (mTLS).** Postgres can authenticate by client certificate, with the certificate common name as the database user and optionally a password as well ([PostgreSQL pg_hba.conf](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)). MongoDB's X.509 mode maps each certificate subject to exactly one `$external` user and requires `requireTLS` ([MongoDB x.509](https://www.mongodb.com/docs/manual/tutorial/configure-x509-client-authentication/)). Identity is the certificate, so a changing home IP does not matter. A Railway-held key is a file in a container with no hardware backing. The notes did not find revocation behaviour for either database, and did not check whether Railway's TCP proxy passes client certificates through untouched. The Mongo page covers standalone instances; replica sets need separate member-authentication setup.

**WireGuard and Tailscale.** WireGuard identifies a peer by its static public key and restricts it only by allowed IP ranges ([WireGuard](https://wireguard.com/)). Tailscale adds user and tag ACLs, posture checks, Tailnet Lock and an SSH mode that needs no local SSH key ([Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh)). Removing a device in the admin console revokes its node key. A Railway service can join a tailnet in userspace mode with a tagged ephemeral auth key ([userspace networking](https://tailscale.com/docs/concepts/userspace-networking)), and Railway documents a Tailscale Forwarder template that replaces the deprecated Subnet Router ([Railway guide](https://docs.railway.com/guides/set-up-a-tailscale-forwarder)). The trust anchor is the auth key in a Railway variable. Inbound connections to a userspace node, raw WireGuard on Railway, plan-level availability of posture and Tailnet Lock, and pricing were not established.

**Cloudflare Access and Tunnel.** A service token is a Client ID and Secret sent as headers, with a one-hour to 30-day rotation grace ([service tokens](https://developers.cloudflare.com/cloudflare-one/identity/service-tokens/)). Access mTLS checks a client certificate at the handshake but is unavailable on the Free plan ([Access mTLS](https://developers.cloudflare.com/cloudflare-one/identity/devices/access-integrations/mutual-tls-authentication/)). The documented SSH route uses `cloudflared access ssh` with a browser identity-provider login ([Cloudflare SSH](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/use-cases/ssh/ssh-cloudflared-authentication/)). The pages retrieved document HTTP only. Whether raw Postgres or Mongo traffic can ride a token or certificate was not confirmed. The service token is a bearer secret in the same class as any environment variable.

**SSH certificates and hardware keys.** OpenSSH `ed25519-sk` keys keep the private key on a FIDO authenticator, and `verify-required` demands a PIN per signature. CA-signed certificates carry principals, a validity window that must be set explicitly, and optional `source-address` and `force-command` limits ([ssh-keygen(1)](https://man.openbsd.org/ssh-keygen.1)). A stolen laptop disk does not yield such a key. These keys protect Jeff's access to the VPS, not a container's access. Secure Enclave SSH on macOS rests on community write-ups, and one forum report says the bundled OpenSSH needed a manually compiled FIDO provider as of January 2025. The notes did not verify late-2026 macOS behaviour, did not fetch the `sshd_config` documentation for disabling password login, and did not retrieve Apple documentation on Secure Enclave client identities.

Railway also offers static outbound IPs on the Pro plan: outbound only, three load-balanced IPs per service, region-specific ([Railway docs](https://docs.railway.com/networking/static-outbound-ips), via a search summary). A staff statement that they are shared rather than dedicated is unverified. A shared IP is a network-location signal, not an identity.

## Where each connection stands against what the notes can support

Mac to VPS is the best-covered path: a hardware-backed FIDO key or SSH certificate, or a Tailscale node, ties access to something Jeff physically holds, and neither depends on his home IP. The notes did not examine the VPS's current configuration, so they say nothing about its present state. Railway to VPS (Mongo and Qdrant) is constrained by Railway's lack of workload identity: a Tailscale node, a database client certificate or a static outbound IP are the options, and each leaves a secret in Railway variables or a shared network signal. Vercel to GeekAPI is not covered by these notes at all, so no Electron or device-identity finding applies to it here. Electron as a client matters only if Jeff chooses to build or adopt a desktop client; the notes do not say he has one. If he does, its main process could use the certificate and storage features above, with the server-side revocation caveat.

## Conclusion

The question that prompted the research, whether OrderStack's use of Electron could show Jeff how to do this, has no answer: no OrderStack evidence exists, and the closest Electron result belongs to an unrelated open-source till. The more useful result is the shape of the constraint. Because Railway attests nothing about a running service, any option's strength is bounded by who can read that service's variables, and the hardware-backed tools (FIDO keys, Secure Enclave) improve only the human end of each connection. A client-side desktop app, Electron or otherwise, cannot hold a secret against an attacker with the user's privileges, so it needs server-side revocation behind it to be worth the effort.

## What this means for securing the connections

1. **OrderStack is not a reference.** The notes found no Electron use and no security documentation, and the site could not be read. If Jeff wants OrderStack examined, he can open getorderstack.com in his own browser and read its download and security pages, or supply a working URL. Decision: whether to pursue this at all, or drop OrderStack as a reference.
2. **Railway cannot attest GeekAPI or GeekRepository** (Railway reply, 2026-04-29). Any identity those services present is a stored secret, a Tailscale auth key, a Cloudflare token, a database client certificate or a static outbound IP. Decision: which secret type Jeff accepts, and who he accepts as able to read Railway variables.
3. **A MAC address cannot serve as a remote device identity** (general networking knowledge, not from the notes). The substitutes are keys and certificates held by the device. Decision: none beyond dropping the idea.
4. **Database client certificates would work for Postgres and Mongo** and are independent of IP (PostgreSQL and MongoDB documentation). Unknowns: certificate revocation behaviour, Railway TCP proxy pass-through, and Mongo replica-set member authentication. Decision: whether to pursue certificate-based database authentication, which needs those checked first.
5. **Tailscale can give a Railway service a tag-based node identity** and is the option with a documented Railway template. Unknowns: inbound connectivity to a userspace node, plan features, pricing. Decision: whether to adopt a tailnet, and who owns the tag and auth-key setup.
6. **Cloudflare covers HTTP endpoints; raw database traffic is unconfirmed.** Access mTLS needs a paid plan. Decision: whether to confirm TCP and database support before considering it.
7. **FIDO-backed `ed25519-sk` keys or SSH certificates protect Jeff's own access to the VPS** and cannot be used by a container. Unknowns: macOS FIDO support in late 2026, and the `sshd_config` settings to disable password login. Decision: whether to move VPS administration to hardware-backed keys, and whether to use certificates with a CA.
8. **If a desktop Electron client is ever built, treat it as a convenience for presenting a certificate or token, not a vault** (Electron documentation and the notes' inference). The needed settings: context isolation and the sandbox (on by default), narrow preloads, IPC sender validation, ASAR integrity with `onlyLoadAppFromAsar`, disabled `RunAsNode` and `NODE_OPTIONS` fuses, code signing, `safeStorage` async API, and server-side revocation. Decision: whether such a client is wanted at all, and whether macOS-only Secure Enclave WebAuthn is acceptable, since no equivalent was found elsewhere.
9. **Vercel to GeekAPI was not covered in these notes.** Decision: whether to commission a separate check of that path, or rely on the existing Vercel machine-identity research already in the repository.
