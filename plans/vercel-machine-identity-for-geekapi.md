# Vercel OIDC shrinks one risk, not the Railway one

**Yes, the portal can authenticate to GeekAPI with Vercel's OIDC token instead of `GEEK_BACKEND_API_KEY`, and it is available on all Vercel plans ([Vercel docs](https://vercel.com/docs/oidc/access-other-services)).** The portal's route handler would read the token with `getVercelOidcToken()` and send it as `Authorization: Bearer`. GeekAPI would verify it with a standard JWT bearer validator against Vercel's published signing keys, and Vercel documents exactly this "connect to your own API" pattern ([Vercel](https://vercel.com/docs/oidc/api)). What it protects against is narrow and real: the portal-to-GeekAPI credential would no longer be a value sitting in an environment-variable store, which is precisely what both the April 2026 Vercel attacker and the October 2026 Railway attacker decrypted. A copy of the token that leaks lasts hours instead of forever, and GeekAPI's logs could say which project and environment made each call. What it does not protect against is just as important. It does nothing about the secrets GeekAPI itself keeps on Railway, because Railway issues no workload-identity token to running services (per Railway staff replies on its community forum, which the research notes do not capture with a source URL, so this report takes it as the owner's stated premise). It does not stop someone who controls a Vercel deployment or account from getting valid tokens, and it moves trust to Vercel's issuer and signing keys, about whose protection the research found nothing. Whether to adopt it, and which environments to trust, are the owner's decisions; the closing section lists them.

## The token is simple to obtain and verify, but the verifier carries all the policy

Vercel gives a deployed Function its token in the `x-vercel-oidc-token` request header, and `@vercel/oidc` reads it, so the call must be made inside the request, not at module load ([Vercel reference](https://vercel.com/docs/oidc/reference)). The token is an RS256 JWT with `iss`, `aud`, `sub` and separate claims for `owner`, `owner_id`, `project`, `project_id` and `environment` ([Vercel reference](https://vercel.com/docs/oidc/reference)). The `sub` has the form `owner:[TEAM_SLUG]:project:[PROJECT_NAME]:environment:[ENVIRONMENT]`, where environment is `development`, `preview`, `production` or a custom-environment slug. Vercel's reference verifier checks only `issuer`, `audience` and `subject`; nothing is enforced for the backend ([Vercel](https://vercel.com/docs/oidc/api)). In ASP.NET Core this maps to JwtBearer with an explicit `ValidIssuer` and `ValidAudience`. The defaults require a signature and an expiry, but they do **not** restrict algorithms or the `typ` header, so both should be set explicitly, and `MapInboundClaims` should be turned off so claim names stay `project_id` and `environment` ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.authentication.jwtbearer.jwtbeareroptions), [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)). The notes found no `ValidSubject` in `TokenValidationParameters`, so checking the project and environment means an authorization policy or an `OnTokenValidated` check, and the notes mark the exact policy API as not yet confirmed.

The dangerous mistakes are all in that policy. A signature and issuer check proves only that Vercel issued the token. In global issuer mode (`https://oidc.vercel.com`) every Vercel customer shares the issuer, and in team mode every project in the team does. The notes therefore point to three pins: the team's `owner_id`, the portal's `project_id`, and `environment == "production"`. IDs are preferred over names because renaming a team or project changes `sub`, `owner` and `project` and "can affect your trust and access control policies" ([Vercel reference](https://vercel.com/docs/oidc/reference)); that preference is the researchers' inference, since Vercel's own example validates `sub`. Environment pinning matters because preview and development tokens are issued by the same issuer for the same project: a pull-request preview that builds and runs receives a legitimately signed `preview` token, and a team member running `vercel env pull` gets a `development` token carrying their `user_id`. Only the backend's refusal of non-production tokens stops them. Unit 42's research on CI/CD OIDC shows how often wildcard conditions such as `repo:org/*` defeat this kind of trust rule, and Vercel's own AWS page shows a looser `project:*` variant next to the strict one ([Unit 42](https://unit42.paloaltonetworks.com/oidc-misconfigurations-in-ci-cd/), [Vercel on AWS](https://vercel.com/docs/oidc/aws)). The notes found no Vercel-specific advisory on OIDC misconfiguration, but that rests on a single search.

Audience and issuer mode interact. The default `aud` is `https://vercel.com/[TEAM_SLUG]`, which names the team but not GeekAPI. Passing a custom `audience` to `getVercelOidcToken()` scopes the token to one service, and it forces the issuer to `https://oidc.vercel.com/[TEAM_SLUG]` in both modes ([Vercel reference](https://vercel.com/docs/oidc/reference)). That removes the mode as a variable, and Vercel marks team mode as the recommended one ([Vercel](https://vercel.com/docs/oidc/access-other-services)). A dedicated audience string also closes a confused-deputy path: a token the portal legitimately obtains for some other purpose cannot be replayed to GeekAPI. Unit 42 warns that audience values can be predictable, so the audience is a boundary alongside the identity pins, not instead of them.

## A stolen token expires in hours, but nothing can revoke it earlier

Function tokens for preview and production live **two hours**, development tokens **twelve**, and builds one ([Vercel reference](https://vercel.com/docs/oidc/reference)). Vercel does not mint a fresh token per execution; it reuses one for the first part of its life, so the token is an ordinary bearer credential. The researchers found no `jti` claim, no revocation mechanism and no sender-constrained option (DPoP or mTLS) in Vercel's documentation. Documentation silence is not proof, so a real token should be inspected before deciding. RFC 6750 says bearer tokens should be one hour or less, so Vercel's two hours is longer than the standard's guidance ([RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html)). Against a static key that never expires, even this is a strictly shorter exposure window. The notes judge replay tracking keyed on a token hash to cost a shared store across Railway instances for little gain on a TLS-only server-to-server call, and recommend TLS, the dedicated audience, project and environment pins, short clock skew and never logging the token. The default clock skew was not verified in the fetched pages, so the notes say to set it explicitly. A cheaper hardening is available: GeekAPI could reject tokens whose `iat` is older than a chosen bound, though that could reject warm functions still using a legitimate reused token and should be tested against real traffic.

## Against the two breaches, it removes a stored secret and leaves the issuer trusted

Both incidents were reads of stored environment variables. Vercel's April 2026 attacker came in through a third-party AI tool, took over an employee's Google Workspace and then Vercel account, and "enumerated and decrypted non-sensitive environment variables"; the incident closed on October 16, 2026 ([Vercel bulletin](https://vercel.com/kb/bulletin/vercel-april-2026-security-incident)). Railway's attacker read encrypted environment variables from its database, and a subset was decrypted with credentials taken from the CI environment, affecting up to 1.85% of workspaces, roughly 100,000 ([Railway report](https://blog.railway.com/p/preliminary-report-october-security-incident)). A static `GEEK_BACKEND_API_KEY` stored on both sides is exactly what such a breach yields. With OIDC the portal holds no durable credential for the GeekAPI call, so a breach limited to reading stored data finds nothing to take for that call. This is the researchers' reasoning, not a tested result: no source evaluates Vercel OIDC under a platform breach, and Vercel's incident bulletin does not mention OIDC. Vercel's own blog argues that encryption at rest does not help "when malicious code can read credentials in production" and recommends OIDC ([Vercel blog](https://vercel.com/blog/death-to-long-lived-static-credentials)), but that post does not mention the incident, and no source ties the two causally.

The limits come from the same reasoning. An attacker who takes over a Vercel account, as in April, can deploy code or pull a `development` token. Pinning `production` blocks the development token, but code deployed to production gets a production token, and no pin on the verifier distinguishes it from the real portal. Anyone who controls Vercel's signing keys could forge any claims, and the notes found no source on how Vercel protects those keys or whether any were exposed. The design also adds a dependency: GeekAPI now trusts a third party's issuer and its JWKS endpoint, so a Vercel outage can become a portal outage. Microsoft's `ConfigurationManager` refreshes keys every 12 hours and on an unknown `kid`, rate-limited to once per five minutes, and keeps a last-known-good configuration by default ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.identitymodel.protocols.configurationmanager-1)). That keeps verification working through a short outage but also lets a withdrawn key keep verifying until restart; the notes cap the exposure at the token's own expiry and leave the keep-or-disable choice open. Fetch failures must fail closed and surface at error level, and a request carrying a Bearer token must never fall back to the API key.

Static IP allowlisting is no substitute. Vercel says an allowlist "confirms where a request came from, but not who sent it"; its static IPs are a shared pool of two per region, apply to every environment including preview, and cost $100 a month per project on Pro ([Vercel static IPs](https://vercel.com/docs/networking/static-ips)).

## The secrets Railway holds stay stored, and the migration has bypass traps

Railway's lack of a workload-identity token is the decisive limit. Vercel's OIDC lets GeekAPI verify the portal without a shared secret, but GeekAPI has no equivalent way to prove its identity to Postgres, Mongo, Qdrant, PayPal, Google or any other service it calls. Those credentials remain environment variables on Railway, the store the October incident read. The researchers state this as an inference from the architecture: the backend's other secrets remain static environment variables and are not covered by this pattern. Railway's advice that users revoke and reapply sensitive variables therefore still applies to everything except the one credential this change removes. The portal's CLAUDE.md also gives the portal a second GeekAPI credential, the owner's Bearer access token, used for tenant routes; the notes did not examine it, and it would be a separate design question.

For the migration itself, the notes suggest turning the key check into a second authentication scheme next to JwtBearer, with a policy that accepts either, then logging which method authenticated each request by name only, and removing the key scheme and its environment variable when the logs show no key use. That sequence is the researchers' design inference; no source prescribes it. The traps they list are middleware that lets unauthenticated requests through on paths missing from an allowlist, a presented-but-invalid Bearer token treated as anonymous, a JWT accepted without the claim policy so that any Vercel customer's token authenticates, endpoints outside the fallback policy, and development settings such as `RequireHttpsMetadata = false` leaking into production. Removing the key means deleting its handler and registration, not just unsetting the variable, and rotating the old key afterwards.

## Conclusion

The change swaps a secret that a platform breach can read for a trust relationship that a platform breach can still abuse, and that swap is worth making only where the second is harder to exploit than the first. For the portal-to-GeekAPI call it is: a read-only breach like the two in 2026 yields nothing durable, and attribution improves. The research did not show that it helps when the attacker acts as the project rather than reading its storage.

The finding that changes the plan is on the Railway side. Because GeekAPI cannot present a workload identity to anything it calls, the largest remaining exposure from an incident like October 21 is untouched by this work, and the portal key is one credential among many. Adopting OIDC removes one entry from the list of secrets to rotate after the next incident; it does not make the list short.

## What this means for GeekAPI and the portal

1. **Pin identity claims, not just the signature (finding: the verifier carries all the policy).** GeekAPI must require the exact team `owner_id`, the portal's `project_id` and `environment == "production"`, compared by ordinal equality, never `project:*` or prefix matching on `sub`. Whether previews may ever call GeekAPI is a product and security decision for the owner; the research gives no basis to allow it. Treat unknown custom-environment slugs as not production.
2. **Decide the issuer mode (finding: shared issuer).** The notes support team mode with a custom audience, which makes both modes yield the same issuer. The owner confirms the mode set in the Vercel project's security settings; the notes did not establish what a new project defaults to.
3. **Choose a dedicated audience (finding: confused deputy).** The owner picks one audience string unique to GeekAPI and not shared with any other service; GeekAPI must reject the default `https://vercel.com/[TEAM_SLUG]` audience.
4. **Set what the .NET defaults leave open (finding: defaults).** Set `ValidAlgorithms` to RS256, `ValidTypes` to JWT, an explicit clock skew, `MapInboundClaims = false`, `SaveToken = false`, and consider `IncludeErrorDetails = false`. Before writing code, inspect a real portal token for `jti` and its actual `iss`, `aud` and claim set, and verify the policy API, since the notes confirmed neither.
5. **Fail closed on JWKS problems (finding: Vercel as a dependency).** A failed metadata fetch is an error-level operator signal, not a caught-and-ignored condition, and a Bearer token never falls back to the API key. Decide whether to keep last-known-good key caching; test the status code returned when the authority is unreachable.
6. **Accept the token's lifetime, or bound it (finding: two-hour bearer token, no revocation).** The owner decides whether to accept up to two hours of exposure or to add an `iat` age bound after testing it against real traffic. Replay tracking is not recommended by the notes.
7. **Migrate without a bypass (finding: migration traps).** Run both schemes under a default and fallback policy, log the authentication method by name only, check every endpoint is covered, remove the key handler and variable when use reaches zero, and rotate the old key. Timing is the owner's call.
8. **Name what still needs stored secrets on Railway (finding: no workload identity on Railway).** Inventory every credential GeekAPI holds as an environment variable, including database, Qdrant, PayPal, Google and any Vercel-related values. Decide which to rotate on what schedule and whether any warrant a different store, noting that this report did not research alternatives. OIDC does not change any of them.
9. **Rename discipline (finding: names change).** Renaming the Vercel team or project can alter `sub`, `owner` and `project`; because the policy pins IDs, a rename should not break it, but the owner should confirm before relying on that.
10. **Open questions the research could not close.** Whether fork-PR previews receive tokens, who on the team can trigger production deploys or pull development tokens, how Vercel protects its signing keys, and whether the owner's Bearer-token path for tenant routes needs the same review. Each needs a check of Vercel's permissions documentation, a Vercel answer, or a separate review before any decision.
